# 产品与架构原则

状态：项目方向与设计约束，不代表能力已实现，也不替代各 change 的行为规范与技术设计。

## 产品目标

agent4jshERP 面向真实 ERP 工作场景，以可用、可靠、可维护的业务助手为建设目标，
计划通过开源方式持续迭代。首批功能可以聚焦少量场景，但应完整处理其中必要的业务边界与失败情况。

用户应能自由表达需求、澄清问题、修改草稿、查看进度，并在中断后继续任务。
成功标准是实际帮助用户完成业务目标，并能核实处理结果。

## 交互方向

统一对话入口承接查询、建议、普通交流和跨领域任务。嵌入 ERP 的全局侧边栏是优先设计方向，
复杂任务可展开到详情区；具体嵌入技术、宿主改动、身份接入与部署方式由后续 design 确定。

业务卡片由结构化数据与预定义组件呈现，关联服务端任务、草稿和版本。
自然语言与表单编辑作用于同一份业务状态，历史卡片应反映过期、取消或已执行状态。

页面上下文与任务上下文分别建模：页面切换不应悄然改变已有任务的业务对象。
宿主提供的商品 ID、仓库或当前页面只能作为输入，服务端仍需校验归属和访问权限。

## 编排方式

主要参考微软的主编排 Agent 与专业子 Agent 模式，并根据业务步骤组合显式工作流。
采用其职责划分和模式选择思想，不因此绑定 Azure、微软 Agent 框架或特定模型供应商。

- 主 Agent 负责持续对话、意图澄清、任务安排、必要的领域委派与结果汇总。
- 专业 Agent 承担有独立推理、领域知识或多步工具需求的任务，以明确的输入输出契约协作。
- 简单查询和确定性运算优先使用工具或业务服务；新增 Agent 应说明其业务价值与边界。
- 对采购确认、审批和单据写入等步骤明确的流程，使用服务端状态与规则控制执行。

专业 Agent 的输入应包含目标、必要上下文、允许能力和任务标识；
输出应区分完成、待补充、部分完成与失败，并附结构化结果、数据依据和未解决问题。
具体字段和状态枚举在对应 change 中确定。

业务确认与权限不能由模型生成一段文字代替；主 Agent 和子 Agent 均通过相同的受控执行服务写入 ERP。
限制委派深度、步骤数、执行时限与资源消耗，明确超时和依赖失败后的处理方式，防止循环委派。

## 真实业务中的质量要求

以下要求应在涉及的 change 中落实为可验证场景，而不是笼统宣称已经具备。

| 关注点 | 设计与验收要求 |
| --- | --- |
| 需求理解 | 支持不完整表达、商品歧义、单位、指代、撤销和修改；关键歧义先澄清 |
| 业务真实性 | 区分采购意向、订单和入库；查询与建议标注必要的数据来源及时间 |
| 写入可靠性 | 校验权限、字段与草稿版本；防重复提交；超时结果未知时先核对再决定重试 |
| 任务连续性 | 持久化必要的任务、草稿和执行状态；覆盖断线、刷新、服务重启后的恢复 |
| 身份与权限 | 绑定真实用户和适用组织范围；专业 Agent 与工具遵守同一访问边界 |
| 用户控制 | 支持修改、取消、确认与必要的人工处理；说明取消是否仍可能伴随已发出的 ERP 写入 |
| 故障恢复 | 显示真实错误、部分完成与待核对状态；保留已完成步骤和后续处理入口 |
| 可观测性 | 关联会话、任务、Agent 调用和 ERP 执行记录，便于定位问题；日志避免保存凭据及不必要的业务内容 |
| 性能与成本 | 测量响应时间、调用次数与成本，根据真实场景确定预算和服务目标 |
| 评估 | 建立可复现业务场景集，覆盖顺利路径、歧义、失败和恢复，并记录真实 ERP 验证结果 |

测试替身可用于本地开发和自动验证，但应明确标识，不能据此声称已完成真实 ERP 集成。
成功率、时延等目标需结合测试环境和基线制定，不使用未经测量的承诺数字。

## 迭代与决策

每个业务增量遵循 OpenSpec 流程，明确范围、契约、验收与兼容性影响。
设计变更应解释选择原因和代价。优先完成范围明确、可验证的闭环，逐步扩展业务覆盖。

本文件不确定数据库、Agent 框架、队列、嵌入技术或部署拓扑；这些选择需要相应设计依据。
当项目方向改变时，同步更新本文件、OpenSpec 上下文和受影响的规范。
