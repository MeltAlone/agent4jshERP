# 采购草稿、确认与执行

状态：版本化草稿、执行状态机及故障恢复的后端数据库/替身测试已通过。已在内置虚构数据环境完成单商品的真实 ERP 正常采购路径，并核对未审核状态、创建者、库存不变及刷新后结果恢复，见 [采购验证记录](purchase-verification.md)。真实 ERP 响应丢失、worker 进程中断与原身份核对恢复已通过独立 API/worker 验收，见 [故障恢复记录](purchase-recovery-verification.md)。多场景、浏览器断流/身份切换及发布就绪验收仍待完成，开发默认关闭写入。

## 业务范围

仅使用已有商品和供应商，人民币、零税、无订金、无折扣及其他费用。采购订单不要求仓库。
确认后目标单据为未审核采购订单，不审核、不入库、不付款。
含税、订金、入库等要求保留为不支持条件并阻止确认；仍需这些条件时转 ERP 手工处理。
如用户明确取消这些要求，可在卡片逐项移除并保存；Agent 不得直接删除已有不支持条件。

数量和单价必须是普通十进制字符串，最多九位整数、六位小数，数量大于零。
当前零价格采购关闭，价格必须大于零；屏蔽价格不等于零。
单位必须与所选扩展 ID、条码及配置换算一致，换算后基本数量超过六位小数时拒绝。
单位展示标签（例如 `箱[12瓶]`、`瓶[基本]`）与业务单位分别处理。草稿服务重新核实当前扩展条码，仅接受该条码的规范单位或其当前完整展示标签；展示标签精确匹配后映射为规范单位，按 ERP 配置计算，不能从括号文本推断换算。原始输入保留用于编辑命令去重，确认快照和执行字段使用规范单位；瓶装条码不能因为同商品配置了箱就按箱采购。

逐行以 `ROUND_HALF_UP` 保留两位金额，总额为行金额之和；基本数量和总额不得超出 ERP `decimal(24,6)` 的整数范围。
订单日期采用 ISO 日期，ERP 时区由 `A4J_ERP_TIMEZONE` 指定，默认 `Asia/Shanghai`。

## 编辑和确认 API

所有资源以 `(connection_id, tenant_id, erp_user_id)` 隔离，沿用会话代次、CSRF 和 Origin 校验。

| 操作 | 接口 | 行为 |
| --- | --- | --- |
| 查询商品 / 供应商 | `GET /lookups/{materials\|suppliers}?query=...` | 有权限的已有实体候选 |
| 新建草稿 | `POST /conversations/{id}/drafts` | `command_id`、可选 `task_id`、完整 `input` |
| 修改 | `PATCH /drafts/{id}` | `command_id`、`expected_version`、`patch`；旧版本 409 |
| 最新草稿 | `GET /drafts/{id}` 或 `GET /tasks/{id}/draft` | 卡片总是读取服务端最新版本 |
| 审阅完整内容 | `POST /drafts/{id}/confirmation` | `expected_version`；返回完整快照和五分钟挑战 |
| 明确确认 | `POST /drafts/{id}/confirm` | `request_id`、`version`、`challenge`；返回唯一执行，202 |
| 取消 | `POST /tasks/{id}/cancel` | `expected_version`；只阻止发送边界之前的创建 |
| 重新编辑 | `POST /drafts/{id}/reopen` | `command_id`、`expected_version`；仅确定未执行的失败 |
| 执行结果 | `GET /executions/{id}` 或 `GET /drafts/{id}/execution` | 实际状态与经核实回执 |
| 手动核对 | `POST /executions/{id}/reconcile` | 原账号授权，仅回查，不创建 |

每次修改产生不可变 revision，并使旧确认失效。重新展示确认单也会使上一个挑战失效。
挑战只保存 hash，绑定 owner、草稿版本与完整内容；“好的”或模型回复不构成执行授权。
同一版本的重复确认返回原执行；不因新的客户端请求标识、worker 恢复或事件重放而重新创建。
取消或完成后的再次采购需要独立任务和新的确认；未知执行不允许通过 reopen 重发。

## 一次发送与回查

确认事务冻结快照并保存独立的持久化 `execution_job`。
worker 以原用户重新验证会话、权限、商品、供应商和换算；业务字段有变化就拒绝发送并保留修复入口。
获取并保存 ERP 单号，再原子写入发送边界标记。只有写入该标记的控制流可以发送一次固定创建 POST。
HTTP 客户端与代理均不得为该接口自动重试。

| 状态 | 意义与下一步 |
| --- | --- |
| queued | 已确认，尚未发送；可取消 |
| dispatching | 标记已持久化，可能已发送；恢复只回查 |
| reconciling | 按原单号有限回查 |
| succeeded | 授权列表、表头和明细均与快照一致，才展示真实订单 |
| rejected | 确定未发送；可重新编辑新版本并重新确认 |
| auth_required | 发送后失去会话或查询权限；原账号重新登录后核对 |
| needs_attention | 结果未知、歧义或不匹配；原单号人工核对或有限手动回查 |
| cancelled_before_send | 在发送边界前取消，无创建请求 |

当前未核实 ERP 业务拒绝响应的无副作用语义，因此发送后即使返回错误，也按未知结果处理。
不会把 HTTP 500、通用成功、暂未查到或模型文字当成确定失败或创建成功。
回查先枚举授权列表并精确匹配原单号，再核对详情 ID、租户、创建者、类型、状态、供应商、日期、备注、单位、数量、金额及无订金/税款等条件。
同时核对商品名称/规格/型号、供应商名称、未删除/未采购状态、空付款账户以及页脚数量；价格不可读、分页不完整、重号或内容不一致时不报告成功。

默认延迟为 `[2,5,15,30,60]` 秒，共五次；`A4J_RECONCILIATION_DELAYS` 可设为 JSON 数组，每项 1–300 秒、最多八项。
手动核对最多追加三轮（`A4J_RECONCILIATION_MAX_ROUNDS`），每轮重新检查原 owner，并保持原单号。
模型不可用不影响确定性结果核对。
此方案优先避免重复创建；ERP 缺少原子幂等键，不能承诺跨系统 exactly-once。

## 开关、升级与恢复

`A4J_PURCHASE_WRITES_ENABLED=false` 为默认值。API 与 worker 都检查开关；新增确认关闭时拒绝创建，已发送执行仍继续回查。
单商品正常路径及核心执行故障恢复已有实测证据，完整场景与发布就绪验收尚未完成；只有隔离虚构数据环境可为验收临时开启，生产启用必须等待对应 OpenSpec 验收证据。

本地验收开启方式：在 `.env` 将该值改为 `true`，执行 `docker compose up -d --no-deps --wait api worker`，随后 `docker compose restart proxy`。刷新 ERP 并打开助手，点击草稿“查看完整确认单”，核对完整内容后由使用者点击“确认创建未审核采购订单”。五分钟确认到期后重新查看确认单；修改字段须保存并重新审阅。恢复禁用时将值改回 `false`，执行相同容器更新命令。默认配置示例继续保持关闭。

升级前停止接收新确认并关闭写入，保存数据库备份和原加密密钥；保留全部执行与单号占用记录。
运行 Alembic 升级、检查 LangGraph 检查点迁移后，再启动 API 与 worker。
未知执行不能用旧备份覆盖、删除执行记录、释放去重身份或通过再次下单猜测处理。
若不得不恢复旧备份，应先逐项交接备份之后可能发送的单号与执行，人工核对 ERP 后再决定是否开放新建。

移除侧边栏只移除入口，不删除 ERP 单据或助手执行证据。
关闭新建开关后应保留 worker 或人工处理待核对执行；用户在发送后取消对话不代表订单回滚。
需要撤销、审核或入库时进入 ERP 的正常业务流程。
执行记录、确认与单号占用目前不由历史清理命令自动删除；需另行定义业务证据保留策略。
