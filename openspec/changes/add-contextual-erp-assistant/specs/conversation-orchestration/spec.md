# Spec Delta

## Purpose

以统一对话承接用户的自由表达、日常交流、业务查询与多轮采购准备，并通过有界的专业协作和明确的业务执行边界提供连续、可解释的回复，使用户不必学习固定格式或理解内部 Agent 分工。

## ADDED Requirements

### Requirement: 自由表达与适当澄清
系统 SHALL 接受不完整自然语言、业务查询、建议和普通交流，不要求固定命令格式。普通交流不得创建采购任务；业务需求缺少关键事实时 SHALL 询问必要信息，不能以闲聊或建议代替执行回执。

#### Scenario: 不完整采购需求
- **WHEN** 用户说想采购一些可乐
- **THEN** 助手识别采购意向，利用已授权事实给出候选或询问缺项，进入可编辑准备流程

#### Scenario: 普通交流
- **WHEN** 用户打招呼或讨论工作安排
- **THEN** 助手自然回复，不生成业务草稿或 ERP 写入

### Requirement: 持续对话中的任务指代
系统 SHALL 在同一会话中支持对当前任务的追加、修改、澄清及暂时转入普通交流；存在多个可指代任务时 SHALL 先澄清。新请求不得静默覆盖其他未完成任务。

#### Scenario: 闲聊后继续修改
- **WHEN** 用户建立采购草稿，闲聊后说把数量改为三箱，且当前只有一个明确采购任务
- **THEN** 助手继续该任务，核实单位后修改同一草稿并返回新版本

#### Scenario: 多个任务存在歧义
- **WHEN** 用户有两个待处理采购任务，又说提交刚才那个
- **THEN** 助手要求选择目标，且不能根据该句直接触发任一写入

### Requirement: 主 Agent 与专业 Agent 的有界协作
系统 SHALL 由主 Agent 统一回复并按需委派采购准备；委派 SHALL 携带任务目标、必要上下文、允许能力和预算，返回明确状态、结构化结果、来源与未决项。专业 Agent 不得扩大权限、无限委派或获得直接 ERP 写入能力。

#### Scenario: 多条件采购准备
- **WHEN** 用户提出需要多步查询和澄清的采购需求
- **THEN** 主 Agent 可以委派采购专业 Agent，并将其结果汇总为同一对话中的建议、澄清或草稿卡片

#### Scenario: 简单库存问题
- **WHEN** 用户只询问已确定商品在指定仓库的库存
- **THEN** 主 Agent 可直接调用授权查询工具，无需为了回复强制启动多个 Agent

### Requirement: 工具和模型调用受预算约束
系统 SHALL 对单次对话运行限制模型调用、工具调用、委派深度及运行时长；超限或专业 Agent 失败时 SHALL 终止新增自动调用，保存已取得的有效结果并说明未完成内容。预算不足不得跳过确认或业务校验。

#### Scenario: 连续查询触及预算
- **WHEN** 一次采购分析持续产生查询并达到配置预算
- **THEN** 助手停止新增调用，返回已核实信息、未完成项和用户可选的继续入口

#### Scenario: 模型服务不可用
- **WHEN** 模型调用失败且受限重试耗尽
- **THEN** 助手明确报告本轮未完成，保留草稿及任务，表单编辑和已发出操作的结果核对仍可独立工作

#### Scenario: 模型响应格式不合法
- **WHEN** 模型返回空内容、截断内容、无效 JSON 或不符合决策结构的内容
- **THEN** 系统拒绝执行该内容，在共享调用和时长预算内最多追加一次格式纠正调用；再次失败或预算耗尽后停止，明确说明模型响应问题，仅在确有查询事实时提示保留结果，不将故障归因于用户缺少信息
- **AND** 运行记录仅保存固定错误分类，不保存模型响应原文、任意校验字段或凭据；非法动作和专业 Agent 权限限制仍然生效

### Requirement: 结构化回复与业务服务边界
系统 SHALL 使用文本和预定义类型卡片呈现查询、澄清、草稿、进度及结果；卡片 SHALL 关联服务端资源与版本。模型不得生成可执行界面代码、任意宿主动作、有效确认凭据或真实业务成功事实。

#### Scenario: 模型声称下单完成但无回执
- **WHEN** 模型输出采购成功而服务端尚无核实的 ERP 执行结果
- **THEN** 界面不显示成功单据卡片，并依据真实任务状态呈现待确认或待核对

#### Scenario: 历史卡片已过期
- **WHEN** 用户打开旧消息中已经被修改、取消或执行的草稿卡片
- **THEN** 卡片显示其当前有效状态，旧卡片不能绕过版本校验再次提交

### Requirement: 查询依据与建议分离
系统 SHALL 区分 ERP 查询事实、用户输入、推断建议及执行结果；业务事实 SHALL 带可追踪来源和查询时间，建议不得伪装成 ERP 已有记录或已完成操作。

#### Scenario: 按库存建议采购
- **WHEN** 助手依据查询到的库存提出采购数量建议
- **THEN** 回复注明库存来源、时间和建议依据，用户仍需确定数量并确认草稿
